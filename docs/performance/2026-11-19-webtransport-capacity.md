# WebTransport capacity investigation — 2026-11-19

## Scope

These are local, controlled measurements, not a 10,000-user capacity claim. The load generator and two Go service nodes ran on the same 16 GiB macOS host. Real headless Chrome 158.0.8127.36 processes opened WebTransport (HTTP/3) sessions. The isolated environment used MySQL 8.4.13, Redis 7.4.5, and etcd 3.5.17. Go was 1.26.10 on darwin/arm64. Test containers, networks, certificates, accounts, and documents were created for each run; no existing project containers or volumes were used.

The load script provisioned separate authenticated users, granted write access, followed Owner Redirect, and joined 20 documents. In the 1,000-user runs, 240 users shared the hot document; in the 2,000-user runs, 480 did. The other users were distributed across the remaining 19 documents. One hot-document client then sent one insert per second, awaiting each `edit_applied` acknowledgment before sending the next. The test checked that the document version increased once per acknowledged edit and sampled active clients, slow-client removals, etcd membership leases, process RSS, and CPU. The Go runtime metrics were added before the heap investigation run.

## Observations

| --- | --- | --- |

| First 2,000-user attempt | One `Connection lost` during the 512-user stage; the run stopped there | No slow-client removal; one etcd sampling timeout. Causality is unproven. |
| Same 2,000-user configuration, rerun | All 2,000 joined; 60 edits acknowledged; no client closed during the edit period | Edit acknowledgment P95: 38 ms; nodes held 480 and 1,520 clients; zero slow-client removals; 442 etcd samples with no errors |
| 2,000 users with Go runtime metric sampling | All 2,000 joined; 30 edits acknowledged; no client closed during the edit period | Edit acknowledgment P95: 148 ms; the 1,520-client node reached about 216 MiB peak allocated heap, 326 MiB peak RSS, and 21,781 goroutines; 378 etcd samples with no errors |
| 2,000 users after Room presence scheduling change | All 2,000 joined without a connection retry; 30 edits acknowledged; no client closed during the edit period | Edit acknowledgment P95: 53 ms; the 1,520-client node reached about 218 MiB peak allocated heap and 21,781 goroutines; 378 etcd samples with no errors and minimum observed lease TTL of 3 seconds |
| Reusable two-node capacity script, 2,000 users | All 2,000 joined; one initial `Connection lost` succeeded on the single recorded retry; 30 edits acknowledged; no client closed during editing | Edit acknowledgment P95: 55 ms; 16 Chrome processes carried at most about 125 sessions each; all 16 required explicit test-owned process termination after graceful shutdown timed out |

The edit latencies from separate runs are **not** a controlled before/after comparison. The Chrome process count, metric collection, host load, and duration can affect them. The last run's higher P95 should be investigated on separate load-generator hosts before attributing it to the metrics change or server code.

A deliberate SIGQUIT diagnostic captured 10,954 goroutines on the node serving about 760 clients. The most frequent stack locations were in `quic-go` and `webtransport-go` stream and connection handling. Application code accounted for approximately one browser writer goroutine and one Redis Presence heartbeat goroutine per active session. That diagnostic intentionally terminated the isolated node; it is not a successful load-test run. Its private stack dump is retained only in a local temporary directory and must not be committed.

During a separate 30-second, 1,000-user hold, the two nodes made approximately 25 and 73 `presence_touch` calls per second for 240 and 760 users. Mean Redis operation duration from the existing histogram was approximately 0.84 and 0.98 ms. No clients disconnected during that hold. This does not establish Redis capacity at 10,000 users.

Before the last run, Room presence updates were changed to schedule one broadcast per 50 ms burst. A joining client still receives the current presence immediately; other clients receive the latest membership snapshot when the scheduled broadcast runs. The browser session keeps only the latest unsent presence snapshot, leaving its reliable edit queue available. This removes repeated all-client presence broadcasts during a join burst. A 1,000-user, 240-hot-user check and the 2,000-user run above completed with all users joined. The separate runs are insufficient to claim a measured latency or memory improvement. In the 2,000-user run, the slow-client counter stayed at zero until session teardown; it rose by three during teardown, after the edit period.

## Test-harness limitation

At 50 and 256 sessions in one Chrome process, Playwright's `browser.close()` returned normally. At 1,000 sessions across four Chrome processes, it timed out even after sessions were closed, browsers were closed sequentially, the isolated servers were stopped, and pages were closed. Those earlier harness processes exited nonzero and remain recorded as failures. Merely canceling WebTransport stream readers and closing writers did not fix the issue.

The reusable `scripts/webtransport-capacity.mjs` now starts each headless Chrome through Playwright's public `BrowserServer` API. After requesting WebTransport session closure and disconnecting the browser controller, it gives the test-owned Chrome process 10 seconds for graceful exit. If needed it calls `BrowserServer.kill()` and checks the child process exit state. In a 1,000-user isolated reproduction with eight Chrome processes, seven exited gracefully and one was terminated. The project-integrated 2,000-user run exited with status zero after all 16 Chrome processes required forced termination; their exit states were observed. That run left 16 temporary Chrome profiles, which were identified by their creation window, matched to the test's 16 browser processes, checked for live process references, and removed. The script now records each browser's exact temporary profile path at launch and removes only that profile after its process exits. A subsequent 1,000-user run verified that all eight recorded profiles were removed and the script exited successfully. This is **bounded test-process cleanup, not a fix for Chrome's graceful shutdown behavior**. The temporary MySQL, Redis, and etcd containers and network were also removed. An unrelated Chrome process that predates these runs was left untouched.

Run the isolated capacity check with `WEBTRANSPORT_LOAD_USERS=1000 scripts/test-phase-11-distributed.sh` or `WEBTRANSPORT_LOAD_USERS=2000 scripts/test-phase-11-distributed.sh`. The script generates temporary authenticated accounts and grants permissions before timing connection and edit stages. For 2,000 users it paces registration and permission changes below the isolated service's existing rate limits; the limits themselves are unchanged. The normal invocation of `scripts/test-phase-11-distributed.sh` still runs the original redirect and failover acceptance test. These runs use one macOS host for the generator and both nodes, so their latency numbers are not directly comparable to the earlier eight-Chrome measurements or a separate-host deployment.

Two project-integrated attempts stopped during account provisioning with HTTP 429, first at registration and then at permission forwarding. No browser capacity result is attributed to those attempts. Pacing both setup paths allowed the subsequent 2,000-user run to reach the measured connection and edit stages without weakening service rate limits.

## Conclusion and next measurement

### Same-host regression after endpoint configuration

The capacity generator now accepts `REST_A_URL`, `REST_B_URL`, `WT_A_URL`, `WT_B_URL`, and `CAPACITY_PAGE_URL`, while keeping its original loopback defaults. This prepares the load generator to target services at separately configured addresses; it does **not** make the current test server reachable from another machine. The server fixture still binds REST, WebTransport, and Vite to `127.0.0.1`, and its certificate covers only loopback names. A separate-machine run therefore still needs an explicitly scoped listener, a certificate valid for the selected address, matching browser origins, and a firewall rule limited to the load generator. MySQL, Redis, etcd, admin, and internal RPC should remain private.

Two regression runs on the same Mac used real Chrome, MySQL, Redis, etcd, and two Go nodes. At 50 sessions, all joined, 30 edits were acknowledged, none closed during editing, and edit acknowledgment P95 was 46 ms. At 256 sessions, all joined without a connection retry, 30 edits were acknowledged, none closed during editing, and edit acknowledgment P95 was 32 ms. The 256-session stage's connection P95 was 235 ms. Both test scripts exited successfully and removed their isolated containers and network. Chrome required bounded forced shutdown for one of one browser processes in the 50-session run and all three in the 256-session run; all corresponding profiles were removed. These runs verify that the configurable generator retains its local behavior. They do not establish cross-machine or 10,000-user capacity.

The local run reports are `/tmp/collab-phase111-ed9269a7f59b.log` and `/tmp/collab-phase111-1f590e0e6982.log`. They are temporary test artifacts and are not intended for Git.

The current evidence does not support removing Room fields as the first memory optimization. Connection-level QUIC/WebTransport goroutines dominate the diagnostic stack; Room ownership was also unevenly distributed in the 20-document sample. Preserve the existing authorization, fencing, OT, and recovery behavior. Next, run longer tests from separate load-generator machines, include multiple hot documents and reconnect waves, and compare per-node heap, goroutines, RSS, CPU, Redis latency, and edit acknowledgment latency. Investigate the Playwright teardown separately. Do not extrapolate these local runs to 10,000 online users or production hardware.

## Quality and safety

After the metrics and Room presence changes, `go test -count=1 ./...`, `go test -count=1 -race ./...`, `go vet ./...`, `go build ./...`, and `git diff --check` passed. The unchanged default real Chrome Owner Redirect and failover integration script passed again after the capacity entry point was added. The new capacity script passed `node --check`; the shell entry point passed `bash -n`. Package tests that require environment variables for real services may skip when those variables are absent; the isolated browser runs above used real MySQL, Redis, and etcd. The process resident-memory metric is platform-dependent; macOS RSS was sampled from the operating system instead. The original ad hoc harness removed its test-only credentials file; the reusable script keeps credentials in process memory. No GCP resources were created, and no commit or push was made for this investigation.
